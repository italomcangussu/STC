# Arquitetura — STC (reserva-sct)
> Camada semântica. Fatos estruturais exatos (arquivos, símbolos, dependentes, testes) → agentmap.

## Visão geral
App de gestão de clube de tênis (reservas, desafios, campeonatos, ranking, financeiro, alunos/professores). React + Vite + TypeScript (raiz do repo, sem `src/`), Supabase (auth, Postgres, realtime, edge functions), PWA (`public/sw.js`, `manifest.json`). Testes: Vitest (`__tests__/`, `*.test.ts`). Deploy via Dockerfile; versão checada por `useVersionCheck` + `scripts/generate-version.js`.

Docs: `docs/financeiro/`. Testes de SQL em PGlite: `__tests__/finance/sql/`.
- Conversas/WhatsApp: tabelas `conv_*` + schema privado `conv_private` em `supabase/migrations/20261007100*`–`1013*` (todas aplicadas em `smztsayzldjmkzmufqcz`, inclusive `101300_joao_pack` em 2026-10-07; `whatsapp-webhook` v27); acesso só admin (`is_admin()`), escrita só por RPC `SECURITY DEFINER`/`conv_svc_*` (service_role); UM histórico (`conv_messages`, `origin` customer/staff/ai/automation/system) e UMA instância UazAPI; edge functions `whatsapp-webhook` (token na URL, só hash no banco), `conversation-operations` (ações do admin que falam com o provedor), `conversations-dispatch` (agendador: automações, retornos), `joao-daily-greeting` (bom-dia diário, mantido pelo dono do clube, auth `x-joao-secret`; UM cron só, `joao-daily-greeting` às 06:45 Fortaleza, criado direto no remoto e fora das migrations; a função reivindica a mensagem antes de enviar para não duplicar no WhatsApp) e `_shared/` (uazChat, uazWebhook, groupMention, aiAgent/*, adminRequest, dispatch); IA propõe e o SERVIDOR grava a reserva só após confirmação explícita (`conv_private.ai_confirm`, regras de reserva espelhadas em SQL); menção direta em grupo é fail-closed e a IA em grupo só liga após verificação humana. - Assinaturas: tabelas `sig_*` + schema privado `sig_private` em `supabase/migrations/20261007120*` (3 arquivos, JÁ aplicados por inteiro no remoto em 2026-10-07; 4 funções com `delete from` — `sig_set_recipients`, `sig_delete_draft`, `sig_publish`, `sig_remove_recipient`, em `docs/assinaturas/PENDENTE_funcoes_com_delete.sql` — foram aplicadas pela API de gestão porque o conector MCP trava nelas); escrita só por RPC `SECURITY DEFINER` (admin: `sig_publish` etc.; sócio: `sig_log_event`, `sig_save_my_cpf`) e `sig_svc_*` (só `service_role`: código de 6 dígitos, gravar assinatura, fila de WhatsApp, lembretes); assinaturas e eventos são APPEND-ONLY, documento publicado é imutável, assinaturas encadeadas por hash (`sig_verify_integrity`); bucket privado `sig-docs` (`<id>/<sha256>.pdf`); código só em hash com sal; reaproveita a UazAPI de Conversas (edge functions `signature-operations` [JWT: pedir/confirmar código, despachar avisos] e `signature-dispatch` [cron com `x-dispatch-secret`: lembretes + fila], PUBLICADAS em 2026-10-07 com cron `signature-dispatch` de 5 min; segredo de cron e checagem em `_shared/dispatch.ts::authorizedBySecret`) e `admin_audit_logs` (`source='signatures'`). Comprovante em PDF (fase 5, `lib/signatures/receipt.ts` + `components/signatures/ReceiptButton.tsx`, jsPDF sob demanda; lê o dossiê de `sig_signatures`; sócio = CPF/telefone mascarados, admin = completo). Docs: `docs/assinaturas/`. Testes: SQL em PGlite `__tests__/signatures/sql/`; edge function (inclui integração com o SQL real) `__tests__/signatures/edge/`.
- Rotas: sem router; `App.tsx` + `lib/publicRoutes.ts` (páginas públicas de campeonato e formulários).
- UI: Tailwind via `index.css`, padrão de modal em `MODAL_PATTERN.md`, design em `DESIGN_SYSTEM.md`/`DESIGN_QUICK_REF.md`.
- Formulários em folha: `components/ui/Sheet.tsx` (sobe da borda no celular; o `Sheet` do financeiro é reexport). Regras puras de pontuação em `lib/pointRules.ts`. Editor de cadastro (`AdminUserEditor`) confirma mudança de função e descarte de dados.

## Fluxos principais
Rota = aba/view em `App.tsx` (sem router). Dados exatos → `.fabuloso/db/uso.md`, `.fabuloso/db/edge.md`.
- Carregar a Agenda: `Agenda.tsx` (`fetchData`) → `fetchAllRows` (páginas de 1000) → `reservations` (+ `profiles`, `courts`, `professors`, `non_socio_students`, `challenges`); `useAgendaRealtime` atualiza ao vivo.
- Desafio: `Challenges.tsx` / `useChallenges` → `challenges` + `reservations` (quadra) → `matches` → ranking (`lib/rankingService.ts`, RPC `get_ranking_cycle_start`) e `ChallengeNotificationPopup`.
- Campeonato: `Championships*`/`ChampionshipAdmin` → `championship_*` (realtime em rounds/registrations) → RPC `finish_championship` / `apply_championship_edition_points` → `point_history`.
- Relatórios do Admin: `AdminReports.fetchMetrics` → `fetchAllRows` (páginas de 1000) → `reservations` por intervalo de datas (+ `profiles`, `consumptions`, `challenges`, `matches`, `courts`).
- Exportar cobranças / Fluxo de caixa: `MembersTab` → `listCharges(filtros, 5000)` e `CashFlowTab` → `movements(..., 5000)` → `pagedRows` → RPC `fin_charge_statements` / `fin_movements`.
- Pendências de sócios: `PendenciesTab` → `listCharges(member_pendency, até 5000)` (avisa se `total_count` > carregadas; totais somados no cliente) + `listPendencyMeta`.
- Créditos de sócios: `MembersTab` (aba Créditos) → `CreditsPanel` → `listCredits` + `profileNames(ids)` → ao escolher o crédito `listCharges({profileId, membership})` → `resolveCredit` (RPC `fin_resolve_credit`).
- Financeiro (admin): `FinanceHub` (abas) → `lib/finance/financeApi.ts` → RPC `fin_*` (SECURITY DEFINER, `request_id`) → `admin_audit_logs`; comprovante por WhatsApp: `whatsapp-webhook` → `finance-receipt-whatsapp` (OCR) → `fin_submit_whatsapp_pendency_receipt`.
- Conversas/João: WhatsApp → `whatsapp-webhook` → RPC `conv_svc_ingest_message` → `conv_messages` (realtime na caixa do admin) → turno da IA (`_shared/aiAgent`) → proposta confirmada → `conv_private.ai_confirm`; envio: `conversation-operations` / `conversations-dispatch` → UazAPI. Bom-dia: cron → `joao-daily-greeting`.
- Assinatura de documento: aba `documentos` (`DocumentSigning`) → `lib/signatures/api.ts` → `signature-operations` → RPC `sig_svc_issue_challenge`/`sig_svc_verify_code` → código por WhatsApp → `sig_signatures` (append-only); lembretes: cron → `signature-dispatch`.
- Cadastrar aluno pelo modal de aula: `Agenda.createStudentFromClass` → INSERT `non_socio_students` (`professor_id` = professor) → INSERT `student_profiles` → gatilhos `*_default_professor` garantem o professor → o aluno entra na aula atual.
- Acesso de atleta: `AdminPanel` → edge `admin-athlete-access` → `access_requests` + `profiles`.
- Push: `lib/notificationService.ts` / `whatsapp-webhook` → edge `send-push` → `push_subscriptions` (RPC `get_admin_push_subscriptions`).

## Convenções que o código não mostra
- Fuso do clube: Fortaleza (`getNowInFortaleza` em `utils.ts`). Dinheiro do financeiro: sempre centavos inteiros (`*_cents`); `student_payments.amount` (NUMERIC legado) só é convertido na leitura.
- Papéis de membro em `MEMBER_ROLES` (`utils.ts`); confirmações via `useConfirm`.
- Erros: `lib/logger.ts` + `lib/humanErrors.ts`.
- `docs/joao-assessor/MAPA.md`: mapa de evolução do João como assessor dos administradores (capacidades, ondas 6 a 8); só documentação, não é código.
- Supabase corta TODA consulta em 1000 linhas sem erro. Leitura de tabela sem janela de data/usuário usa `lib/fetchAllRows.ts`: `fetchAllRows((from, to) => supabase.from(t).select('*').order(...).order('id').range(from, to))`; a ordem termina em `id` para a paginação não repetir nem pular linha. Opções no 2º argumento: `{ pageSize?, maxRows? }` (`maxRows` = "até N linhas"). Já com janela e sem necessidade: AdminPanel (90 dias), Athletes, Challenges/Klanches/SuperSet, `useReservations`. RPC que devolve conjunto também é cortada em 1000: `pagedRows` (interna de `financeApi.ts`, usada por `listCharges` e `movements`) pagina por `p_limit`/`p_offset` até o teto pedido (SQL limita `p_limit`: cobranças 1000, fila de comprovantes 500, movimentos 5000; a ordem do SQL é total). Mocks de Supabase em teste precisam aceitar `.range()`; mock de RPC paginada devolve página CHEIA para pedir a seguinte. Leituras escritas como `from('t' as never)` não aparecem em `db/uso.md`: auditar por busca de texto.
- Professor padrão: o clube tem um único professor (Diego Memória, `professors`) e todo aluno (`non_socio_students`, `student_profiles`) nasce com ele. Vive NO BANCO, para valer em qualquer caminho de escrita (Agenda, admin, João/`adm_dependent_create`, importações): gatilhos `trg_*_default_professor` (BEFORE INSERT OR UPDATE OF `professor_id`) → `set_default_professor()` → `default_professor_id()`, que só devolve o id quando existe EXATAMENTE UM professor ativo (zero ou mais de um: nulo, o banco não adivinha). Motivo: a RLS de `non_socio_students` só deixa INSERT para admin ou professor gravando o próprio `professor_id`, e `ProfessorProfile` filtra alunos por `professor_id`. Com um segundo professor ativo a regra deixa de preencher sozinha (exigirá escolha na tela). `AdminStudents` ainda monta `professor_id: null` para dependente (o gatilho corrige).
- `non_socio_students` e `student_profiles` não têm gatilho de auditoria (cadastros e apagamentos não aparecem em `admin_audit_logs`; só `reservations` tem). Investigar acesso: log do gateway via API de gestão do Supabase, `GET /v1/projects/{ref}/analytics/endpoints/logs` com `sql` sobre `logs` (`source='edge_logs'`; `request.path`, `request.method`, `response.status_code`, `request.sb.auth_user`), janela máx. 24h, `SUPABASE_ACCESS_TOKEN` de `.env.local` sem imprimir; erros do Postgres em `source='postgres_logs'`.
